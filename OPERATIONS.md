# Read-only operations and audit

The primary administrator can create a **Read-only operator** under **Users**. The operator lands on **Operations**, with service checks, counts for queued and running sync jobs, aggregated failure categories, and disk trends. The operator can manage their own password and sessions. The role cannot open any mailbox, view raw jobs or log files, export diagnostics or backups, or change system settings. Giving an existing user this role requires removing or moving their source accounts first. Changing a role or disabling a user invalidates their existing sessions.

Capacity is sampled every five minutes from the same bounded probes used by system diagnostics. The 24-hour view shows the lowest available values in each 15-minute interval; the seven-day view uses hourly intervals. A gap is missing evidence, not zero capacity. A missing inode value is shown separately from zero. A changed volume identity starts a separate series. Capacity collection failures leave gaps and do not block the mail application. See the dashboard for immediate readings and account pages for sync block and retry status.

The primary administrator can filter and export the displayed **Administration audit** records. Filter by a sync job number or the exact restore or update operation ID to correlate available records. The audit distinguishes completed Web requests from confirmed restore and update outcomes, including CLI restores recorded by the local restore journal. Terminal records have no HTTP status and are attributed to the local operation rather than guessing a Web actor. A submitted request does not mean it completed; an update reported as requiring recovery is not a verified rollback. Existing local history can be picked up after startup, within the source's retention and the audit's time limit. The audit contains no passwords, tokens, URLs, addresses or raw request contents. Failed sign-ins are grouped by time and outcome. The local audit is not tamper-proof and is not a substitute for an external audit archive.

The separate `db/operations.db` stores up to 10,000 audit records from the last 30 days and up to seven days of sampled capacity. The app's normal configuration backup and restore do not export or rewind this file. If the operations database is temporarily unwritable, core mail actions continue and the page reports that some observations could not be saved. The data disk remains subject to the administrator's host-level retention and backup policy.

## Separate Linux storage volumes

On Linux, capacity checks also reject a read-only mount or the loss of a separate volume that the running application already observed. For example, an unavailable log volume postpones sync even when the underlying root disk has free space. A restore-points volume alone does not stop normal sync. Diagnostic details show the reason; affected accounts continue to show the capacity block and retry time. If a known volume is replaced with a different one on purpose, verify the path before restarting the application.

For protection starting with the first capacity check, put the required mount points in the Web service environment. On OpenRC, use the service configuration file `/etc/conf.d/mail-aggregator`:

```sh
export MAIL_AGG_REQUIRED_MOUNTS='{"logs":"/srv/mail-data/logs","mail":"/srv/mail"}'
```

On systemd, use a service drop-in with `[Service]` and `Environment='MAIL_AGG_REQUIRED_MOUNTS={"logs":"/srv/mail-data/logs","mail":"/srv/mail"}'`, then reload the unit configuration. Restart Web in a maintenance window after changing either setting.

Use the actual mount point, not a directory underneath it. Valid purposes are `application`, `database`, `credentials`, `logs`, `cache`, `temporary`, `restore_points` and `mail`. Leave this setting unset for ordinary root-disk installations. If mail capacity is obtained from an older Dovecot helper, update the helper through the manual installer or set `MAIL_AGG_MAIL_STORAGE_PATH` to the local Maildir storage path readable by the service. This check protects sync admission and running sync jobs; configure service mount dependencies and make the underlying directories unwritable to the service account to prevent any writes when a volume is absent.

## Notification subscriptions

The primary administrator can opt into **Storage capacity alerts and recoveries** separately from **Sync failures and recoveries**. Existing configurations keep their sync subscription; storage alerts start disabled. Once enabled, a newly detected low-space or inode condition opens one incident per measured volume. After two healthy observations at least one minute apart, the matching recovery becomes eligible, provided the failure was delivered. Changing destinations or restoring the application data cannot cause an old incident to be delivered to a new destination or replayed from an earlier database generation. An unavailable probe never emits a recovery by itself.

Capacity payloads contain the event and incident IDs, an opaque volume ID, the purpose labels, and a fixed reason code. They do not contain paths, hostnames, fake job IDs, or account details. In notification settings, **The receiver deduplicates by event ID** is off by default, including for existing endpoints. Enable it only after confirming your HTTPS receiver ignores duplicate `Idempotency-Key` (or `eventId`) values for the entire retry period. Without confirmation, a timeout, connection loss, HTTP 408 or 5xx, or an interrupted send is marked **Delivery needs review** and is not automatically retried. Confirmed receivers can retry on those outcomes with backoff and the same ID and header, up to eight attempts. An explicit HTTP 429 still retries with backoff; it does not erase uncertainty from an earlier attempt. Telegram has no deduplication option. Disabling notifications, changing the endpoint, or withdrawing confirmation ends the authorization to retry already ambiguous attempts. Reconfirming allows future attempts to use this policy, but does not resume events already marked for review. If a completely full database volume prevents recording an incident, the current block is still shown on the system and account pages.


**Configuration restore results** and **Application update results** are each off by default. Once opted in, the app reports only subsequent results: a verified configuration restore or reversal, an installed app update, a verified rollback, or a terminal update failure. A request being accepted, waiting, deferred, or recovering is not a completion. An unresolved rollback or restore must be investigated from the local records and is not sent as a success. Update notifications require the managed local updater; no notice is produced for manual package changes on platforms without it. Refresh the root-owned updater with the documented manual install when activating this feature; an older updater that did not positively record a live rollback cannot report that rollback to this subscription.

The operation event contains the stable operation ID and outcome, plus source and destination application versions for updates. It contains no filesystem paths, email data, destination or raw error. Operation notification policy (`notification.json` under the private application data directory) is migrated from the older secrets directory once. Policy, delivery attempts, and deduplication receipts (`db/notification-operations.db`) are independent of the configuration backup and the updater's replaceable application database. New backups omit both the local configuration and any legacy copy. Old archives can still be restored, but cannot activate their old notification destination; keep those older archives private because they may still contain the old key. Do not copy an older host-level snapshot of these files over a live instance. Changing the destination or opting out abandons pending operation events from that subscription; opting back in starts a new cutoff. The same Webhook confirmation and retry policy applies to these events. Records already handed off to an external provider cannot be recalled. The public delivery history is retained for 30 days; operation receipts are retained so old application snapshots do not replay it.
